You are the backend developer for FreshPass (Laravel). Implement Solo “working with / affiliation” as a REQUEST + APPROVE/REJECT flow. Display only. No booking, billing, staff, or payout behavior changes.

CONTEXT — what already exists
- Solo owners can currently send `workingWithBusiness` (camelCase) on `POST /api/user` (multipart). Empty string / "0" / "null" / "undefined" means clear.
- Responses use snake_case: `working_with_business_id`, `working_with_business` (full BusinessResource) on `GET /api/user/details` and `GET /api/business/details`.
- Only Solo-plan owners (`subscription_is_single === true` AND subscription active) can set this. Anyone else: ignore the field, rest of profile still saves.
- On Solo → Business plan upgrade, affiliation is already meant to be cleared in `SubscriptionService::clearWorkingWithBusinessOnUpgrade()` via `supersedePreviousBusinessSubscriptions()`. Keep that, and EXTEND it (see Upgrade below).
- `GET /api/businesses` is the active-business list used by the app picker. Affiliation target must be an existing **active** business, and must not be the Solo user’s own business.

CHANGE THE PRODUCT RULE
Do NOT instantly attach the Solo user to the host shop when they save a business id.
`workingWithBusiness` now creates (or updates) an **affiliation request** in `pending` status.
Customers must NOT see the affiliation (“working with”) until the host **approves**. Their work address is always their own saved location and is always editable.

DATA MODEL
Create a dedicated affiliation table (suggested: `business_affiliations`):
- `id`
- `solo_user_id` (the Solo owner user id)
- `solo_business_id` (the Solo owner’s own business)
- `host_business_id` (the shop they want to appear at)
- `status`: `pending` | `approved` | `rejected` | `removed`
- `requested_at`, `responded_at`, `responded_by_user_id` nullable
- `removed_at`, `removed_by` enum: `host` | `upgrade` | `solo_cancel` | `solo_switch` nullable
- unique: one **active** row per Solo business. Active = `pending` OR `approved`.
Rules:
- Only one pending OR approved affiliation per Solo business at a time.
- If Solo already has `pending` and submits a different `host_business_id`, replace the pending request (cancel/supersede the old pending; notify the old host that the request was withdrawn; notify the new host of the new request). Location is unchanged (pending never copied location).
- If Solo submits the **same** already-approved host id again: no-op (do not create a duplicate request).
- If Solo submits `workingWithBusiness` empty while `pending`: cancel the pending request (`removed` / withdrawn, removed_by=solo_cancel), notify the host that the request was cancelled. Do NOT clear location (they never received host location).
- If Solo submits empty while `approved`: do **not** let Solo unlink themselves this way (host must remove, or upgrade auto-clears). Return 422 like “Ask the shop to remove your affiliation.”
- Host cannot be the Solo’s own business.
- Host business must be `active = true`.
- Rejected rows stay in history; Solo may send a new request later to the same or another host.

SWITCHING TO A DIFFERENT SHOP (CRITICAL — client specified)
If the Solo user is **already approved** with host A, then in Edit Profile they search, select a **different** host B, and tap Update:

1. The old affiliation with A is **completely removed immediately** — do not wait for B to approve or reject.
   - Old row status=`removed`, removed_by=`solo_switch`
   - Do **not** wipe the Solo owner’s saved work address. Location stays under their control.
   - Send `update_location` as a **reminder** to review/edit their workplace address (they may still have shop A’s address saved).
2. Create a new `pending` request to B.
3. Notifications for this switch (all in-app panel + push):
   - Solo: old affiliation ended with A (they chose a different shop).
   - Solo: `update_location` reminder — review or update your work address.
   - Host A: this Solo is no longer affiliated with your shop.
   - Host B: new affiliation request from this Solo.
   - Solo: request sent to B (see “request sent” below). Wait for B to approve or reject.
4. What happens later does **not** restore A:
   - If B **approves**: attach B. Optionally **prefill** Solo location with B’s address if you still copy on approve (see Location). Solo can edit after. A stays gone.
   - If B **rejects**: Solo stays unaffiliated. Keep whatever address they already have. Notify Solo rejected. Do **not** bring A back. A is gone in both cases.

KEEP APP CONTRACT WHERE POSSIBLE
Edit Profile already posts `workingWithBusiness` on `POST /api/user`. Keep that as the Solo entry point.
- Field omitted: do not change affiliation state (same as today).
- `workingWithBusiness = {id}`: create/replace pending request as above. Do **not** set `working_with_business_id` as approved until host approves.
- `workingWithBusiness = ""`: cancel pending only (see above).

SAME SHOP ON PROFILE-ONLY UPDATE (CRITICAL — do not re-fire requests)
If the Solo user only changes name, phone, photo, etc. and the picker is still the **same shop as before**, do **not** treat it as a new affiliation request.

“Same as before” means the posted `workingWithBusiness` id equals:
- the current **approved** `host_business_id`, OR
- the current **pending** request’s `host_business_id`

In that case:
- Backend: **no-op** on affiliation. Do not create a new row, do not reset `requested_at`, do not send any affiliation notifications to Solo or host, do not touch location. Save the rest of the profile normally (name etc.).
- Frontend (put this in the frontend guide): only `formData.append("workingWithBusiness", …)` when the picker value **changed** from the value that was loaded on screen open (approved id OR pending host id). If they only edited name/phone/photo, **omit the field entirely** so the existing approved link or pending request stays untouched.

Only when the posted id is **different** from the previous approved/pending host:
- run the switch / replace-pending flow (old remove + notifications + new request), as specified above.

If they already have approved A and they submit A again (same id): no-op. Same if they already have pending B and they submit B again: no-op.

Add (snake_case):

- `working_with_business_request` — if a pending request exists:
  `{ id, status: "pending", host_business_id, host_business: { id, title, logo_url, owner, address fields... }, requested_at }`
  else null
Customer-facing `GET /api/business/details?business_id={id}` — THIS IS THE MAIN CUSTOMER SCREEN API (home → open a salon):
This is the same call the app uses when a customer taps a shop from Home (e.g. “Touseef salon”). If that business is Solo **and** has an **approved** affiliation, the response **must** include the affiliation data. Do not omit it. Pending = null.

BUSINESS (HOST) APIs
Auth: host business owner (or whoever can manage that business). Must own `host_business_id`.

1) List requests
GET /api/affiliation-requests
Query: status=pending|approved|rejected|removed|all (default pending), page, per_page
Response items:
- id, status, requested_at, responded_at
- solo_user: id, name, profile_image_url, phone optional
- solo_business: id, title, logo_url, logo
This is what the shop uses to approve/reject. The app will add a **new business-side screen** that lists these and lets the owner Approve / Reject / Remove.

2) Approve
POST /api/affiliation-requests/{id}/approve
- Only host of that request, only if status=pending
- Set status=approved, responded_at, responded_by
- Previous approved affiliation with another host should already be gone if Solo switched (see Switching). Still defend: if any other approved row exists for this Solo, remove it (do not wipe Solo’s saved address).
- **Prefill (optional convenience, one-time):** copy host location onto the Solo business location module **only as a starting point**, and only if you do this copy at all. Never lock the field. Solo can edit immediately after via the existing business-location API/screen.
- Notify Solo: approved (in-app panel + push)

3) Reject
POST /api/affiliation-requests/{id}/reject
- Only host, only pending
- status=rejected
- Do NOT copy location
- Do NOT restore any previous host
- Notify Solo: rejected (in-app + push)

4) Remove an approved affiliation
POST /api/affiliation-requests/{id}/remove
(or DELETE)
- Only host, only approved
- status=removed, removed_by=host
- Do **not** delete the Solo owner’s saved work address.
- Notify Solo:
  A) affiliation removed (in-app + push)
  B) a second notification type **update_location**: reminder to review or manually update their work address
- Customers keep seeing whatever address the Solo currently has saved until they edit it.

LOCATION — SOLO ALWAYS CONTROLS THEIR WORK ADDRESS (client confirmed)
Affiliation is **not** the only way a Solo address exists. The Solo owner can create and **manually edit** their workplace location at any time on the existing business-location screen (`business-location` module), including:
- before any affiliation request
- while a request is pending
- after the host has approved
- after affiliation is removed, rejected, switched, or they upgrade

Never disable or 403 the location update API for Solo because they are affiliated.

Customer-facing address (business details, booking, appointment) is always the Solo business’s **own saved location** — whatever they last saved. Do **not** overlay/replace it at read time with the host address (that would take control away from Solo).

On affiliation **approve** (optional one-time prefill only):
- You MAY copy the host shop’s address onto the Solo location record so customers initially see the shop they work at.
- If you copy, treat it as a prefill. If Solo later updates location, that edit wins forever; do not overwrite their edit on later host profile changes.
- Suggested flag: `location_source = affiliated_host` after copy, then `location_source = manual` after Solo PATCHes location. Never copy again while `manual`.

When affiliation is **removed** (host remove OR upgrade OR solo_switch) or **rejected**:
- Do **not** wipe street, city, state, zip, lat, long, complete_address.
- Send `update_location` as a reminder to review/edit. They can keep the current address or change it.

`update_location` notification still fires on remove / switch / upgrade so they are prompted to review the address. Copy should say they can update it themselves, not that it was deleted.

VALIDATION / ERRORS
- Inactive or missing host id: 422 on workingWithBusiness as today.
- Not Solo: ignore workingWithBusiness, save the rest of the profile.
- Approve/reject/remove by non-host: 403.
- Wrong status transitions: 422.
Do not 500. Keep profile update success even if notification push fails (queue notifications; log failures).

DISPLAY-ONLY REMINDER

- lets the host edit the Solo business
It only: pending request → host decision → display of host identity on the Solo business for customers. Work address is owned by the Solo owner and is always manually editable.
